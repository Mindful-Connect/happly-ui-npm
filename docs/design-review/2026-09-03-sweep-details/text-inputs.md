## Follow-up — consuming `required` / `describedBy` from the form-field context

The lead extended `FormFieldContextValue` with `required?: boolean` and `describedBy?: string`
(`FormField.Root` sets `describedBy` only while a hint or error is rendered, and reuses one
`<id>-message` element for both).

## Second pass

### What the first pass missed

**It never drove a component.** The first pass read class strings and ARIA attributes and
verified them in a rendered DOM — but it only ever *looked* at the components, it never typed
into one. Three of this pass's HIGH findings are the same shape: a value-resolution chain
`explicit prop ?? RHF binding ?? nothing`, with no internal state at the end of it. When a
consumer uses the component the way the docs show it (`<CurrencyInput.Root />`), there is no
value source and no change handler, so the control is **inert** — you can type and nothing
happens. It is invisible to a class-string review (no class is involved), invisible to an ARIA
review (every attribute is correct), and invisible in Storybook because every story for those
components is controlled. `tag-input`, `date-input` and `combo-box` all keep an internal
fallback; `currency-input`, `digit-input` and `socials-input` did not. **Check the uncontrolled
path of every component that accepts a `value`.**

The second pattern is **dead motion**: classes that compile but sit on an element the library
unmounts (`select.tsx`'s whole `data-[state=closed]` block never runs), and a class that does not
compile at all (`blur-0`) which this very sweep had already caught and fixed in another group's
file. Cross-group knowledge did not travel — the fix note lived in `actions-and-feedback.md`
while the same bug shipped in `password-input.tsx`.
